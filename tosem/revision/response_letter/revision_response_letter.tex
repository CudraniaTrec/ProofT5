We thank the reviewers and the editor for their valuable comments. We have
revised our paper accordingly. Every reviewer comment is quoted below in
italics, followed by our response and by a summary of the changes we made in
the paper; section and page numbers refer to the revised manuscript
(45 pages).

\textbf{Summary of changes.} The revision adds two Java benchmarks
(HumanEval-Java and TransCoder-GFG) that enlarge the Java evaluation to 186
tasks, a statistical analysis with 95\% intervals and exact paired tests
(App.~D), a task-level failure taxonomy (App.~C), runtime and pruning
measurements of the constrained decoder (RQ2), a comparison with three
decoder-only models of 7B--30B parameters (Table~3), and a comparison with
four reliability-oriented generation methods (RQ3, Table~5). It also adds a
Limitations subsection (Sec.~6.3) on the encoder-decoder dependence,
dynamically typed languages, and type-system expressiveness.

\begin{itemize}[leftmargin=1.4em]

\response Thanks. We have followed the directions of the meta-review in full. Each of the six
concerns is addressed with new experiments or new text, and none of them is
answered by wording alone:

\begin{itemize}[leftmargin=1.4em]
  \item \textbf{Failure analysis.} Every test task of the three Java benchmarks is classified into four categories in App.~C (p.~42--43, Table~8), with two representative cases; the dominant residual mode of TyFlow is well-typed but semantically wrong code. Detailed response: Comment~1.6.
  \item \textbf{Benchmarks.} HumanEval-Java (146/16) and TransCoder-GFG (414/103) are added and normalized to the MBJP format, so the Java evaluation spans 186 test tasks from three independent sources, analyzed jointly in App.~D (p.~44). Detailed responses: Comments~1.1, 2.1.
  \item \textbf{Scalability.} RQ2 measures the pruning strength of each component, the beam-exhaustion behavior, and the per-step and per-task runtime (up to $2.74\times$ the unconstrained base); scaling to richer type systems is discussed in the Limitations subsection. Detailed responses: Comments~1.5, 2.2.
  \item \textbf{Larger and more recent LLMs.} Zero- and few-shot pass@1 results for MiMo-7B, Qwen3-14B, and Qwen3-30B-A3B on all four benchmarks are added (Table~3, p.~26): on Java they outperform the fine-tuned 2B models, on SuFu none solves a single task zero-shot. Detailed responses: Comments~1.3, 2.3.
  \item \textbf{State-of-the-art techniques.} RQ3 is rewritten as a five-method comparison on MBJP (rejection sampling, SynCode, Repilot, iterative compiler repair) on one leak-clean frozen checkpoint; none of the four external methods significantly improves functional correctness, while TyFlow-2B is the best of all compared methods. Detailed responses: Comments~3.1, 3.2.
  \item \textbf{System cost.} The runtime analysis is reported in RQ2
        together with the component ablation it belongs to: per-step and
        per-task wall time of the same 220M model in the four configurations,
        with an explanation of where each cost comes from and why syntactic
        pruning even \emph{lowers} the per-task total. For the compared
        external methods, the RQ3 setup states each method's computational
        budget. Detailed responses: Comments~2.2, 3.3.
\end{itemize}

\section*{Response to Reviewer 1}

We thank the reviewer for the positive assessment of the formalization, its generality over grammar-based approaches, and the ablation study.

\begin{revcomment}{Comment 1.1.}
The SuFu test set has only \textasciitilde58 tasks (20\% of 290), and the Java
test set has only \textasciitilde61 tasks (10\% of 608). These are very small
test sets, and the results may not be statistically robust. The authors should
report confidence intervals or conduct significance tests. A difference of
1--2 tasks passing or failing could shift pass@1 by several percentage

\emph{[Weaknesses:]} Small test sets raise concerns about statistical
reliability. [\dots] Missing failure analysis and confidence intervals.
\end{revcomment}

\response Thanks for this comment. We addressed the concern on both sides: we enlarged the Java
evaluation, and we added a full statistical analysis.

\textbf{(1) Larger test sets.} The two added Java benchmarks bring the Java evaluation from 67 to 186 test tasks from three independent sources; SuFu remains a 58-task test set by construction, and we now state its role explicitly.

\textbf{(2) Intervals and paired tests.} New App.~D (p.~44) reports 95\% intervals and exact paired tests for every comparison; the outcomes are:

\begin{itemize}[leftmargin=1.4em]
  \item \textbf{220M, SuFu (58 tasks):} all four differences significant (pass@1 $p=3.86{\times}10^{-2}$, pass@10 $p=2.35{\times}10^{-3}$, FSP $p=7.20{\times}10^{-3}$, CER $p=6.94{\times}10^{-18}$).
  \item \textbf{220M, Java (67 tasks):} only CER is significant ($p=6.98{\times}10^{-11}$); the pass-rate tests are underpowered (one and five extra tasks leave only 11/19/24 discordant pairs), and the appendix says so instead of claiming significance.
  \item \textbf{2B, Java pooled (186 tasks):} all four differences significant (pass@1 $p=2.09{\times}10^{-3}$, pass@10 $p=5.36{\times}10^{-4}$, FSP $p=7.65{\times}10^{-4}$, CER $p=1.25{\times}10^{-19}$); this analysis carries the statistical conclusion.
  \item \textbf{2B, SuFu (58 tasks):} the compilation-error difference is significant ($p=5.55{\times}10^{-17}$, all 55 baseline-error tasks favoring TyFlow); pass@1, pass@10, and FSP favor TyFlow in the same direction as at 220M but are not significant at $n=58$, for the same underpowering reason as the 220M Java block.
\end{itemize}

We report this mixed outcome rather than smoothing it over: the improvements
are consistent in direction everywhere, and where the evidence is too thin (220M Java and 2B SuFu), the appendix states the power limitation and
points to the analyses that do reach significance.

\textbf{(3) One row pair follows the re-trained results.} As noted at the
end of this letter, the submitted results come from 2025 runs whose
checkpoints are not available here, so all models were re-trained and
re-evaluated. This affects the 2B SuFu pair: the re-trained baseline is
31.03/41.38/6.19/59.31 and TyFlow-2B is 36.21/48.28/5.53/0.00, again better
on all four metrics. Both rows are backed by preserved per-task arrays.

\begin{revcomment}{Comment 1.2.}
On Java, TyFlow-220M improves pass@1 from 10.45\% to only 11.94\%, less than
1.5 percentage points absolute. While pass@10 improves more substantially,
the pass@1 gain is marginal, given the test set size. The paper should
discuss why Java gains are smaller.\smallskip

\emph{[Weaknesses:]} The Java results are modest, and the subset restriction
introduces potential selection bias.
\end{revcomment}

\response Thanks. We agree that this gain is not convincing on its own. We made three changes: we explain the mechanism, we extend the Java
evidence well beyond the 220M figure quoted here, and we address the
selection-bias concern directly.

\textbf{(1) Why the 220M Java pass@1 gain is small.} Type constraints cannot make a semantically wrong program right; what they remove is uncompilable output, which shows up in pass@10 (20.90\% $\to$ 28.36\%) and CER (35.52\% $\to$ 1.53\%) rather than in pass@1. App.~C shows why the top-1 candidate can still be semantically wrong.

\textbf{(2) The effect is much larger at 2B and on the added benchmarks.} At
the 2B scale, pass@1 rises 13.43\% $\to$ 25.37\% (MBJP), 31.25\% $\to$
50.00\% (HumanEval-Java), and 19.42\% $\to$ 30.10\% (TransCoder-GFG), with
CER falling to 0.45\%/1.30\%/2.75\%. The 220M Java figure is therefore best
read as the low-resource end of a scale trend, which the revision now shows.

\textbf{(3) Stronger baselines, not weaker ones.} The added benchmarks' baselines were deliberately strengthened (learning rate $10^{-5}$, 30 passes, holdout-selected checkpoints): this raised HumanEval-Java from 12.50\% to 31.25\% pass@1 and TransCoder-GFG from 13.59\% to 19.42\%, so the TyFlow gains are measured against stronger baselines; the pooled 186-task differences remain significant (Comment~1.1).

\textbf{(4) Selection bias.} The Java-subset toolchain admits the tasks it
supports (approximately 78\% of MBJP). The revision states this admission
filter explicitly in App.~B and mitigates it with the two additional
benchmarks drawn from independent sources; no claim in the paper now rests on
the MBJP subset alone.

\begin{revcomment}{Comment 1.5.}
Completeness says that for any well-typed program, there exists a synthesis
derivation tree. But during generation, the LM must find the right sequence
of decisions. If the LM makes a wrong choice early, it may be unable to
recover. The paper does not discuss the branching factor of the search space
or the likelihood of the LM making correct decisions in practice. Beam
search partially addresses this, but the theoretical analysis gives no
bounds on how many beams are needed.\smallskip
The paper does not quantify the pruning rate in Section 5.3. What fraction
of candidate tokens are eliminated at each level? This would help readers
understand the practical search space reduction.
\end{revcomment}

\response Thanks for this criticism. We now measure the constrained decoder instead of only arguing
about it, and we state explicitly what the completeness theorem does and does
not imply for search.

\textbf{(1) Pruning rates.} Instrumenting the decoder on the SuFu tasks (beam~10, 330-step budget) gives: syntactic pruning removes 59.1\% of all vocabulary proposals, and type pruning a further 8.2\% (type checking is applied only to the high-probability candidates about to enter the beam, which is why its rate is lower). A final, complete type check on finished derivations rejects 21.2\% of the completed candidates (113/533).

\textbf{(2) Branching factor and beam behavior.} The revision separates two
claims that were previously conflated: (i) by construction, pruning removes
only ill-formed or ill-typed expansions, so every possibly correct
derivation survives; (ii) the residual risk comes from beam search itself,
which keeps only a fixed number of candidates per step, so the correct
candidate may in theory fall outside the beam and the retained candidates
then dead-end. In the instrumented run this never happens: under beam~10 no
task dead-ends, and every task retains at least one grammar- and type-valid
expansion at every step. This is reported as an empirical observation, not as
a general guarantee, and we no longer claim bounds we cannot prove.

  \item \textbf{Added} Sec.~6.2.2 (p.~27): ``How much the constraints prune'': instrumented rates (59.1\% syntactic, 8.2\% type, 21.2\% final check) and the 330-step budget.
  \item \textbf{Added} Sec.~6.2.2 (p.~27): ``Whether the constraints over-prune'': the constructive argument, the beam-size residual risk, and the zero dead-end observation.

\begin{revquote}{Revised manuscript, Sec.~6.2.2, ``How much the constraints prune'' (p.~27)}

the SuFu tasks (beam 10, 330-step budget): syntactic pruning removes 59.1\%
of all vocabulary proposals, and type pruning a further 8.2\%. The lower
rate is expected: type checking is more expensive, so it is applied only to
the high-probability candidates about to enter the beam. Such candidates are
rarely ill-typed, yet pruning them matters, for they would otherwise expand
within the beam and crowd out well-typed derivations. Type checking during
search is provisional (only completed AST fields are checked); the whole
program is checked once when the derivation finishes, and this final check
rejects 21.2\% of the completed candidates.
\end{revquote}

\begin{revquote}{Revised manuscript, Sec.~6.2.2, ``Whether the constraints over-prune'' (p.~27)}
By construction, pruning removes only ill-formed or ill-typed expansions, so
every possibly correct derivation survives. The residual risk is beam search
itself, which retains only a fixed number of candidates per step: the correct
candidate may in theory fall outside the beam, and the retained candidates
then dead-end. In our experiments this never occurs: under the beam-10
setting, no task dead-ends, and every task retains at least one grammar- and
type-valid expansion at every step.
\end{revquote}

\begin{revcomment}{Comment 3.6.}
TyFlow relies strongly on the typing system of the language, but how would
it work on a dynamically typed language such as Python? Thus, the author
should acknowledge this in the threat to validity to make this paper more
robust.
\end{revcomment}

\response Thanks for this comment. A dedicated limitations paragraph now states the obstacle: TyFlow needs the type derivation to be computable from the program text, which is what makes training data automatic in the two evaluated languages (290 SuFu programs, 608 Java training tasks); in a dynamically typed language the derivation depends on control flow and runtime information, so decision sequences cannot be extracted from existing code, the Data Usability property breaks, and adaptation is left to future work.

\begin{revquote}{Revised manuscript, Sec.~1, ``Data Usability'' (p.~3)}
The decision sequences of $S$ and source code should be automatically and
bidirectionally convertible, enabling both the extraction of decision
sequences from existing programs and the reconstruction of programs from
generated decision sequences.
\end{revquote}

\begin{revquote}{Revised manuscript, Sec.~6.3, ``Dynamically typed languages'' (p.~29)}
The current design of TyFlow relies on a type system in which the type
derivation of a program can be computed automatically from the program text,
so that existing code can be converted into our decision-sequence format.
Dynamically typed languages such as Python still have typing rules to a degree, but the type derivation cannot be read off the program text alone, since types depend on control flow and runtime information. [\dots] Parsing and adapting such languages is left to future work.
