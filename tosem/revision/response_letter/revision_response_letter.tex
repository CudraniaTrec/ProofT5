We thank the reviewers and the editor for their valuable comments. We have
revised our paper accordingly. Every reviewer comment is quoted below in
italics, followed by our response and by a summary of the changes we made in
the paper; section and page numbers refer to the revised manuscript
(45 pages).

\textbf{Summary of changes.} The revision adds two Java benchmarks
(HumanEval-Java and TransCoder-GFG) that enlarge the Java evaluation to 186
tasks, a statistical analysis with 95\% intervals and exact paired tests
(App.~D), and a task-level failure taxonomy (App.~C). It also adds runtime
and pruning measurements of the constrained decoder (RQ2). The comparison
with other generation methods now covers three decoder-only models of
7B--30B parameters (Table~3) and four reliability-oriented approaches
(RQ3, Table~5). A new Limitations subsection (Sec.~6.3) discusses the
encoder-decoder dependence, dynamically typed languages, and type-system
expressiveness.

\section*{Response to the Editor}

\begin{revcomment}{Editor's comment.}
All the reviewers agree that the paper investigates an important topic.
However, reviewers also point out major concerns that need to be addressed
and responded to, hence my recommendation for a Major Revision. In the
following, I have provided some of the critical concerns raised by the
reviewers.

\begin{itemize}[leftmargin=1.4em]
  \item Missing failure analysis
  \item Limited evaluation benchmarks
  \item Missing discussion on scalability
  \item Missing comparison with larger and more recent LLMs
  \item Missing comparison with state-of-the-art techniques
  \item Missing analysis of the system's cost
\end{itemize}
\end{revcomment}

\response Thanks. Each of the six concerns is addressed with new experiments or new analyses, as summarized below:

\begin{itemize}[leftmargin=1.4em]
  \item \textbf{Failure analysis.} Every test task of the three Java benchmarks is classified into four categories in App.~C (p.~42--43, Table~8), with two representative cases; the dominant residual mode of TyFlow is well-typed but semantically wrong code. Detailed response: \commentref{1.6}.
  \item \textbf{Benchmarks.} HumanEval-Java (146/16) and TransCoder-GFG (414/103) are added, so the Java evaluation spans 186 test tasks from three independent sources, analyzed jointly in App.~D (p.~44). Detailed responses: Comments~\commentref{1.3}, \commentref{2.1}.
  \item \textbf{Scalability.} RQ2 measures the pruning strength of each component, the beam-exhaustion behavior, and the per-step and per-task runtime (up to $2.74\times$ the unconstrained base); scaling to richer type systems is discussed in the Limitations subsection. Detailed responses: Comments~\commentref{1.2}, \commentref{2.2}.
  \item \textbf{Larger and more recent LLMs.} Zero- and few-shot pass@1 results for MiMo-7B, Qwen3-14B, and Qwen3-30B-A3B on all four benchmarks are added (Table~3, p.~26): on Java they outperform the fine-tuned 2B models, on SuFu none solves a single task zero-shot. Detailed responses: Comments~\commentref{1.5}, \commentref{2.3}.
  \item \textbf{State-of-the-art techniques.} RQ3 is rewritten as a five-method comparison on MBJP (rejection sampling, SynCode, Repilot, iterative compiler repair) on one leak-clean frozen checkpoint; none of the four external methods significantly improves functional correctness, while TyFlow-2B is the best of all compared methods. Detailed responses: Comments~\commentref{3.1}, \commentref{3.2}.
  \item \textbf{System cost.} The runtime analysis is reported in RQ2
        together with the component ablation it belongs to: per-step and
        per-task wall time of the same 220M model in the four configurations,
        with an explanation of where each cost comes from and why syntactic
        pruning even \emph{lowers} the per-task total. For the compared
        external methods, the RQ3 setup states each method's computational
        budget. Detailed responses: Comments~\commentref{2.2}, \commentref{3.3}.
\end{itemize}

The individual reviewer comments, with the corresponding responses, follow.

\section*{Response to Reviewer 1}

We thank the reviewer for the positive assessment of the formalization, its generality over grammar-based approaches, and the ablation study.

\phantomsection\label{com:1.1}
\begin{revcomment}{Comment 1.1.}
The example language ($\lambda\!\rightarrow$) is extremely simple. While it
serves the pedagogical purpose well, readers may reasonably wonder whether
the approach scales to languages with subtyping, polymorphism, type
inference, overloading, or mutable state. The paper partially addresses this
by evaluating on Java, but the overview could better acknowledge the gap
between $\lambda\!\rightarrow$ and real languages.\smallskip

The restriction to first-order unification deserves further discussion.
Higher-order unification arises naturally in languages with higher-order
functions and polymorphism. The authors should discuss what happens when
this restriction is violated and what classes of type systems are
excluded.\smallskip

\emph{[Weaknesses:]} The restriction to first-order unification and
encoder-decoder architectures limits near-term applicability.
\end{revcomment}

\response Thanks for these questions. We added scoping text in three places, and we answer each half of
the comment separately.

\textbf{(1) The example language.} The overview now acknowledges the gap
concretely (quoted below): it enumerates what $\lambda\!\rightarrow$ omits
relative to real languages --- subtyping, polymorphism, type inference,
overloading resolution, and mutable state, exactly the features the reviewer
names --- states that the minimal calculus is a deliberate choice for
exposition, and points to the evaluation languages, to the scope of the rule
framework (Sec.~3), and to the Limitations discussion of richer type systems
(Sec.~6.3).

\textbf{(2) First-order unification.} Section~3 now states what the restriction excludes (type systems requiring higher-order unification, which is undecidable in general) and what an extension would need; the quoted passage names this class explicitly.

\textbf{(3) Type-system expressiveness and the architecture.} A dedicated Limitations subsection (Sec.~6.3) now covers the omitted Java features, the CHC framing, and what migration would involve (quoted below). The encoder-decoder dependence is treated in the same subsection and in the response to \commentref{2.3}. Empirically, the two evaluated settings are a functional language (SuFu, 58 test tasks) and a Java subset admitting about 78\% of MBJP (186 Java test tasks in total), and TyFlow improves over its base model in both; the added paragraph states precisely what these settings do not establish.

\changesmade{\begin{itemize}[leftmargin=1.2em,itemsep=1pt,topsep=2pt]
  \item \textbf{Added} Sec.~2 (p.~9): the overview now enumerates the gap between $\lambda\!\rightarrow$ and real languages (subtyping, polymorphism, type inference, overloading resolution, mutable state) and points to the evaluation and the Limitations discussion.
  \item \textbf{Added} Sec.~3 (p.~12): what the first-order restriction excludes (higher-order unification) and what an extension would need.
  \item \textbf{Added} Sec.~6.3, ``Type-system expressiveness'' (p.~30): the omitted Java features, the CHC framing, and future work on richer type systems.
\end{itemize}}

\begin{revquote}{Revised manuscript, Sec.~2 (p.~9) -- the acknowledged gap between the example language and real languages}
The $\lambda^{\rightarrow}$ language above serves for exposition: it is
deliberately minimal, containing only the base type \tcode{bool}, function
types, and explicitly annotated, monomorphic bindings. Real languages
additionally involve subtyping, polymorphism, type inference, overloading
resolution, and mutable state, none of which $\lambda^{\rightarrow}$
exercises. The evaluation (Sec.~6) therefore runs TyFlow on Java and SuFu
instances with fuller, though still restricted, type systems; the scope of
the underlying rule framework is stated in Sec.~3, and how the approach
would extend to richer type systems is discussed in Sec.~6.3.
\end{revquote}

\begin{revquote}{Revised manuscript, Sec.~3 (p.~12) -- what first-order unification excludes}
First-order unification is decidable and admits efficient algorithmic
solutions, making it suitable for our synthesis framework. This restriction
excludes type systems that require \emph{higher-order unification}, which
arises naturally with higher-order functions and polymorphism and is
undecidable in general. Extending TyFlow to such systems would need a
decidable fragment (e.g., patterns) or a different variable-acquisition
mechanism, and our formal results do not automatically carry over.
\end{revquote}

\begin{revquote}{Revised manuscript, Sec.~6.3, ``Type-system expressiveness'' (p.~30) -- type-system expressiveness as a limitation}
Both evaluated type systems are relatively simple compared with the
mainstream languages that have evolved over decades, such as C++: the
implemented Java subset omits subtyping hierarchies, overload resolution,
and mutable-state-related features, and SuFu's type system targets fusion
optimization. [\dots] The restriction is practical rather than conceptual: writing
and modeling the concrete typing rules and designing the parser for a richer
system make experimentation much harder, and our measurements on SuFu and
the Java subset do not establish how the approach scales to such languages.
Migrating TyFlow to richer type systems, and even to systems such as linear
types that can to some extent guarantee functional properties of the code,
is a direction for future work.
\end{revquote}

\phantomsection\label{com:1.2}
\begin{revcomment}{Comment 1.2.}
The practical implications of completeness deserve more discussion.
Completeness says that for any well-typed program, there exists a synthesis
derivation tree. But during generation, the LM must find the right sequence
of decisions. If the LM makes a wrong choice early, it may be unable to
recover. The paper does not discuss the branching factor of the search space
or the likelihood of the LM making correct decisions in practice. Beam
search partially addresses this, but the theoretical analysis gives no
bounds on how many beams are needed.\smallskip
The paper does not quantify the pruning rate in Section 5.3. What fraction
of candidate tokens are eliminated at each level? This would help readers
understand the practical search space reduction.
\end{revcomment}

\response Thanks for this criticism. We now measure the constrained decoder, and we state explicitly what the
completeness theorem does and does not imply for search.

\textbf{(1) Pruning rates.} Instrumenting the decoder on the SuFu tasks (beam~10, 330-step budget) gives: syntactic pruning removes 59.1\% of all vocabulary proposals, and type pruning a further 8.2\% (type checking is applied only to the high-probability candidates about to enter the beam, which is why its rate is lower). A final, complete type check on finished derivations rejects 21.2\% of the completed candidates (113/533).

\textbf{(2) Branching factor and beam behavior.} The revision separates two
claims that were previously conflated: (i) by construction, pruning removes
only ill-formed or ill-typed expansions, so every possibly correct
derivation survives; (ii) the residual risk comes from beam search itself,
which keeps only a fixed number of candidates per step, so the correct
candidate may in theory fall outside the beam and the retained candidates
then dead-end. In the instrumented run this never happens: under beam~10 no
task dead-ends, and every task retains at least one grammar- and type-valid
expansion at every step. This is reported as an empirical observation, not as
a general guarantee.

\changesmade{\begin{itemize}[leftmargin=1.2em,itemsep=1pt,topsep=2pt]
  \item \textbf{Added} Sec.~6.2.2 (p.~27): ``How much the constraints prune'': instrumented rates (59.1\% syntactic, 8.2\% type, 21.2\% final check) and the 330-step budget.
  \item \textbf{Added} Sec.~6.2.2 (p.~27): ``Whether the constraints over-prune'': the constructive argument, the beam-size residual risk, and the zero dead-end observation.
\end{itemize}}

\begin{revquote}{Revised manuscript, Sec.~6.2.2, ``How much the constraints prune'' (p.~27) -- the measured pruning rates}
To measure the pruning strength, we instrument the constrained decoder on
the SuFu tasks (beam 10, 330-step budget): syntactic pruning removes 59.1\%
of all vocabulary proposals, and type pruning a further 8.2\%. The lower
rate is expected: type checking is more expensive, so it is applied only to
the high-probability candidates about to enter the beam. Such candidates are
rarely ill-typed, yet pruning them matters, for they would otherwise expand
within the beam and crowd out well-typed derivations. Type checking during
search is provisional (only completed AST fields are checked); the whole
program is checked once when the derivation finishes, and this final check
rejects 21.2\% of the completed candidates.
\end{revquote}

\begin{revquote}{Revised manuscript, Sec.~6.2.2, ``Whether the constraints over-prune'' (p.~27) -- the over-pruning argument and zero dead-ends}
By construction, pruning removes only ill-formed or ill-typed expansions, so
every possibly correct derivation survives. The residual risk is beam search
itself, which retains only a fixed number of candidates per step: the correct
candidate may in theory fall outside the beam, and the retained candidates
then dead-end. In our experiments this never occurs: under the beam-10
setting, no task dead-ends, and every task retains at least one grammar- and
type-valid expansion at every step.
\end{revquote}

\phantomsection\label{com:1.3}
\begin{revcomment}{Comment 1.3.}
The SuFu test set has only \textasciitilde58 tasks (20\% of 290), and the Java
test set has only \textasciitilde61 tasks (10\% of 608). These are very small
test sets, and the results may not be statistically robust. The authors should
report confidence intervals or conduct significance tests. A difference of
1--2 tasks passing or failing could shift pass@1 by several percentage
points.\smallskip

\emph{[Weaknesses:]} Small test sets raise concerns about statistical
reliability. [\dots] Missing failure analysis and confidence intervals.
\end{revcomment}

\response Thanks for this comment. We addressed it in two ways: a larger evaluation, and a full statistical analysis.

\textbf{(1) Experimental setup.} Two Java benchmarks are added:
HumanEval-Java, the Java port of HumanEval (146 training and 16 test tasks),
and TransCoder-GFG, the GeeksForGeeks programs released with TransCoder (414
training and 103 test tasks); both follow the task format of MBJP, and their
construction and split statistics are documented in App.~B (p.~37--40). The
Java evaluation therefore grows from 67 to 186 test tasks across three
independent sources. SuFu remains a 58-task test set by construction (the
language has 290 programs in total).

\textbf{(2) Statistical methodology.} New App.~D (p.~44) pairs every
baseline--TyFlow run on the same tasks (ten candidates per task) and reports,
for each metric, a 95\% interval together with an exact two-sided paired
test: Wilson intervals and McNemar tests on discordant pairs for
pass@1/pass@10, a $t$-interval over per-task ranks plus an exact sign test
for FSP, and a Wilson interval over candidates plus an exact sign test on
per-task error fractions for CER.

\textbf{(3) Results, organized by language.} The significance of the results
differs by language and scale: for Java, only CER is significant at 220M
while all four differences are significant at 2B; for SuFu, all four are
significant at 220M while at 2B only CER remains clearly significant.
\begin{itemize}[leftmargin=1.4em]
  \item \textbf{Java.}
        \textbf{At 220M} (67 tasks), the two pass-rate gains are small
        in magnitude and the task set is small, so they are not particularly
        significant (pass@1 moves only from 10.45\% to 11.94\%); the
        compilation-error difference, however, is highly significant,
        $p=6.98{\times}10^{-11}$, 35.52\% $\to$ 1.53\%.

        \textbf{At 2B}, pooling the three Java benchmarks into 186 tasks
        changes the picture: the larger task count is clearly reflected in
        the $p$-values, and all four differences are significant (pass@1
        18.28\% $\to$ 30.11\%, $p=2.09{\times}10^{-3}$; pass@10 33.33\%
        $\to$ 46.24\%, $p=5.36{\times}10^{-4}$; FSP
        $p=7.65{\times}10^{-4}$; CER 20.32\% $\to$ 1.77\%,
        $p=1.25{\times}10^{-19}$).
  \item \textbf{SuFu (58 tasks).} The task count likewise drives the
        $p$-values here.

        \textbf{At 220M}, all four differences are significant (pass@1
        24.14\% $\to$ 37.93\%, $p=3.86{\times}10^{-2}$; pass@10
        $p=2.35{\times}10^{-3}$; FSP $p=7.20{\times}10^{-3}$; CER
        $p=6.94{\times}10^{-18}$).

        \textbf{At 2B}, the gains on the two pass-rate metrics (25.86\%
        $\to$ 36.21\% and 37.93\% $\to$ 48.28\%) are not
        particularly significant ($p=0.286$ and $p=0.307$), although the 95\%
        intervals still indicate an improvement (e.g., TyFlow-2B's pass@1
        interval [25.05,49.07] lies above the baseline's [16.35,38.38]); the
        compilation-error difference remains clearly significant (71.21\%
        $\to$ 0.00\%, $p=6.94{\times}10^{-18}$).
\end{itemize}

Across all comparisons the differences point in the same direction; where the
evidence is thinner (220M Java and 2B SuFu), Appendix~D states the power
limitation and points to the analyses that reach significance.

\phantomsection\label{com:1.4}
\begin{revcomment}{Comment 1.4.}
On Java, TyFlow-220M improves pass@1 from 10.45\% to only 11.94\%, less than
1.5 percentage points absolute. While pass@10 improves more substantially,
the pass@1 gain is marginal, given the test set size. The paper should
discuss why Java gains are smaller.\smallskip

\emph{[Weaknesses:]} The Java results are modest, and the subset restriction
introduces potential selection bias.
\end{revcomment}

\response Thanks. We agree that the 1.5-percentage-point number is not convincing on its own. The revision responds in three ways: it explains the cause, it extends the Java evaluation, and it addresses the selection-bias concern.

\textbf{(1) Why the 220M Java pass@1 gain is small.} On SuFu the baseline starts from a low-resource language with many type errors, so the type constraints have many errors to fix. On Java the baseline has already been trained extensively on the language, so there is little room for improvement at this scale; what the constraints still remove is the uncompilable output, and that improvement appears in pass@10 (20.90\% $\to$ 28.36\%) and CER (35.52\% $\to$ 1.53\%).

\textbf{(2) The gain grows with the model scale.} The 220M figure comes from the smallest model on the smallest Java test set, so on its own it says little about what TyFlow achieves as capacity grows; at the 2B scale the same comparison yields much larger numbers, with pass@1 rising 13.43\% $\to$ 25.37\% (MBJP), 31.25\% $\to$ 50.00\% (HumanEval-Java), and 19.42\% $\to$ 30.10\% on TransCoder-GFG, with CER falling to 0.45\%/1.30\%/2.75\%. The 220M figure is therefore the smallest-scale point of this trend, which the revision now documents.

\textbf{(3) The selection-bias concern.} This is a genuine scope limitation of the approach. The method requires programs to be expressible within the modeled type system and grammar: the toolchain admits about 78\% of MBJP, and the two added benchmarks are similarly restricted to constructs the toolchain supports. The revision now states this explicitly in App.~B, and the Limitations subsection (Sec.~6.3, p.~30) discusses why the restriction is practical rather than conceptual.

\phantomsection\label{com:1.5}
\begin{revcomment}{Comment 1.5.}
The paper compares only with fine-tuned CodeT5 and T5Gemma2 variants. The
absence of any comparison with modern LLMs is a notable gap. The authors
could at least report zero-shot pass rates for state-of-the-art proprietary
and open-weight LLMs on the same benchmarks to contextualize the absolute
numbers.\smallskip

\emph{[Weaknesses:]} No comparison with modern decoder-only large-scale code
models.

\response Thanks for this suggestion. We compared TyFlow with rejection
sampling, SynCode, Repilot (\emph{Copiloting the Copilots}), and iterative
compiler repair on MBJP, all running on the same frozen checkpoint under the
same sampling protocol. The question is whether these external mechanisms,
which operate only on the model's output at decoding time, can match
internalizing the type constraints into the model itself. The results show
they cannot: all four filter, mask, or repair candidates without changing
the model's own distribution over programs, whereas TyFlow changes that
distribution by encoding the typing rules into the model.

\textbf{SynCode} constrains decoding at each step by masking tokens that would violate the grammar, so every output is syntactically well-formed. It reduces the compilation-error rate (26.12\% $\to$ 21.34\%) but leaves the solved sets unchanged: constraining syntax does not help with semantic correctness, because a well-formed program can still compute the wrong result.

\textbf{Repilot} is the method proposed in \emph{Copiloting the Copilots}. It
pairs the LM with the Eclipse JDT completion engine, pruning tokens that the
engine cannot legally complete. In our run its pruning rarely fires, for two
reasons. First, following the original implementation, punctuation and
keyword tokens are accepted without querying the engine, so a large share of
the model's token proposals are never checked at all. Second, when the
engine is queried, it is queried at an incomplete position, where its
completion list is permissive: JDT can legally continue almost any partial
prefix, so few proposals are actually rejected. Repilot therefore behaves
close to unconstrained decoding: compilation errors barely move (26.12\%
$\to$ 25.97\%), and the solved sets are unchanged.

\textbf{Rejection sampling} is the only external method that changes any outcome, adding three solved tasks at pass@10 and one at pass@1, but neither difference is statistically significant.

\textbf{TyFlow-2B} solves 17/67 at pass@1 and 29/67 at pass@10 with only 3/670 compilation errors, the best result among all compared methods. The type constraint guarantees compilable code at the source (CER 0.45\%), rather than filtering or repairing what the model already produces.

\phantomsection\label{com:3.3}
\begin{revcomment}{Comment 3.3.}
The TyFlow system requires multiple LLM calls to obtain all synthesis
decisions. To show the practicality of TyFlow, it is important to provide an
analysis of the system's cost for generating the program.
\end{revcomment}

\response Thanks for this question. We first clarify the base case, then explain what our method adds on top of it.

\textbf{(1) The base case is a single encoder--decoder call.} The system is not a multi-LLM pipeline: the encoder processes the prompt once, and the decoder generates the output token by token, reusing the encoder's representation throughout. There are no repeated LLM calls to separate models.

\textbf{(2) What our method adds on top of this base.} During decoding, we add syntactic pruning (checking each generated token against the grammar), type pruning (checking completed AST fields against the type system), and a dynamic typing context (re-encoding the synthesis goal as it evolves). Each of these adds moderate per-step cost, but the encoder's computation is fully reused, so the total does not grow proportionally.

\textbf{(3) The measured cost.} RQ2 now times the same 220M model in the four component configurations, reporting per-step (31.1 $\to$ 32.4 $\to$ 43.7 $\to$ 59.6\,ms) and per-task totals (5.70 / 5.34 / 11.07 / 15.62\,s, i.e.\ $2.74\times$ the unconstrained base). Each increment has a stated cause (per-step type checking; re-encoding the evolving synthesis goal). For the compared external methods, the RQ3 setup states each method's computational budget rather than leaving costs unstated.

  \item \textbf{Added} Sec.~6.2.2 (p.~27): per-step and per-task runtime for the four configurations (Table~4).
  \item \textbf{Added} Sec.~6.2.3 (p.~28): the computational budget of each compared external method.
\end{itemize}}

\begin{revquote}{Revised manuscript, Sec.~6.2.3 (p.~28) -- the rejection-sampling budget}

\phantomsection\label{com:3.5}
\begin{revcomment}{Comment 3.5.}
The TyFlow system was mainly evaluated on small models. Evaluation on larger
models (decoder-only, billions of parameters) is unexplored. The authors
should consider extending the evaluation to larger models.
\end{revcomment}

\response Thanks for this comment. This question is already answered in
detail under \commentref{1.5} (the added zero- and few-shot comparison, and its
data-leakage caveat) and \commentref{2.3} (the same results read against the
open question of larger models, plus the architectural discussion); we
restate the analysis and conclusions here so that they can be read on
their own.

\textbf{The added comparison.} Three open-weight decoder-only models
(MiMo-7B, Qwen3-14B, Qwen3-30B-A3B; 7B--30B parameters) are evaluated on
all four benchmarks, zero- and few-shot, under a separate prompt-based
protocol kept distinct from the trained results (Table~3, p.~26); the
evaluation now spans five model scales.

\textbf{The two-sided analysis.} On Java the decoder-only models are
clearly stronger in absolute terms than the fine-tuned 2B models, and the
revision says so plainly, since this is exactly what such a comparison is
for; it also flags a possible data-leakage risk for the Java comparison,
because few-shot prompting brings these models little or no gain over

does not eliminate type errors in the setting the method targets, so it
does not substitute for the type-guided representation. Whether TyFlow
itself can be adapted to decoder-only architectures is discussed in the
Limitations (Sec.~6.3), including what the adaptation would cost; that
adaptation is left to future work.

\phantomsection\label{com:3.6}
\begin{revcomment}{Comment 3.6.}
TyFlow relies strongly on the typing system of the language, but how would
it work on a dynamically typed language such as Python? Thus, the author
should acknowledge this in the threat to validity to make this paper more
robust.
\end{revcomment}

\response Thanks for this comment. A dedicated limitations paragraph now states the obstacle: TyFlow needs the type derivation to be computable from the program text, which is what makes training data automatic in the two evaluated languages (290 SuFu programs, 608 Java training tasks); in a dynamically typed language the derivation depends on control flow and runtime information, so decision sequences cannot be extracted from existing code, the Data Usability property no longer holds, and adaptation is left to future work.

\begin{revquote}{Revised manuscript, Sec.~1, ``Data Usability'' (p.~3) -- the Data Usability property}
The decision sequences of $\mathcal{S}$ and source code should be automatically and

\end{revquote}

\begin{revquote}{Revised manuscript, Sec.~6.3, ``Dynamically typed languages'' (p.~30) -- the dynamic-language limitation}
The current design of TyFlow relies on a type system in which the type

so that existing code can be converted into our decision-sequence format.
