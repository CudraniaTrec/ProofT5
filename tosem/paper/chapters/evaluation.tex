\section{Evaluation \label{sec:evaluation}}
We design our evaluation to answer the following research questions.
\begin{itemize}
    \item \textbf{RQ1:} How does \mainname compare with the existing code generation methods?
    \item \textbf{RQ2:} How does each component of \mainname contributes to the overall performance?
    \item \textbf{RQ3:} How does \mainname compare with reliability-oriented generation approaches, including rejection sampling, token-level constrained decoding, completion-engine repair, and iterative compiler-feedback repair?
    \item \textbf{RQ4:} How does \mainname compare with variants that generate the type derivation tree and the program separately instead of simultaneously?
\end{itemize}

\subsection{Experimental Setup}

\subsubsection{Benchmark}
To evaluate the generality of \mainname, our evaluation considers two languages with very different characteristics, SuFu~\cite{DBLP:journals/pacmpl/JiZPXH24} and Java.
%Correspondingly, we used two datasets: the SuFu dataset and the MBJP~\cite{DBLP:conf/iclr/AthiwaratkunGWL23} dataset.
\begin{itemize}
 \item \textbf{SuFu} is an ML-style functional language designed for automatic program optimization. This language uses a customized type system for extracting operations for optimization on data structures.
 %
 This language has limited code resources, making it representative for evaluating \mainname under low-resource conditions.

 We collect SuFu programs from its GitHub repository, which comprises 290 programs with test cases. For each program, we manually supply a natural language description, along with the relevant inductive definitions and library functions, thus collecting a dataset of code generation tasks.
 %
 This dataset is then split randomly into a training set of 80\% tasks and a test set of 20\% tasks.
 
 \item \textbf{Java} is a popular imperative language with a sophisticated type system. In a balance between the implementation cost and the expressiveness, we implement a subset of Java that preserves its core syntax while omitting advanced features like lambda expressions.

 We consider the MBJP dataset~\cite{DBLP:conf/iclr/AthiwaratkunGWL23} in our evaluation, which is the Java version of the popular MBPP dataset. Our Java subset covers the MBJP tasks admitted by our toolchain, which we split randomly into a training set of 608 tasks and a held-out test set of 67 tasks.

 \item \textbf{HumanEval-Java} and \textbf{TransCoder-GFG} are two additional Java benchmarks introduced in this revision to broaden the evaluation beyond MBJP. HumanEval-Java normalizes the Java port of HumanEval~\cite{DBLP:journals/corr/abs-2107-03374} into the MBJP prompt, class, and test-harness format, and TransCoder-GFG does the same for the GeeksForGeeks programs released with TransCoder~\cite{DBLP:conf/nips/LachauxROC20}. Both benchmarks are aligned with the MBJP task style and therefore measure in-distribution extension of the MBJP setting: HumanEval-Java uses a fixed split of 146 training and 16 test tasks, and TransCoder-GFG uses a fixed 80/20 split of 414 training and 103 test tasks. A lineage audit additionally found that 5 of the 16 HumanEval-Java test tasks occur in the training lineage of an ancestor checkpoint of \mainname-2B, so the 16-task result is labelled ancestor-mixed. Dataset construction, normalization, and audits are detailed in Appendix~\ref{appendix-benchmark}.
\end{itemize}

More information about SuFu, Java, and the datasets can be found in Appendix~\ref{appendix-benchmark}.

\subsubsection{Models}
We implement \mainname based on CodeT5~\cite{DBLP:conf/emnlp/0034WJH21}, a family of encoder-decoder models for code understanding and generation. We adopt the 220M variant of CodeT5 as our base model for subsequent training and refer to our model as \mainname-220M. 
We also evaluate \mainname on T5Gemma2~\cite{zhang2025t5gemma2seeingreading}, a more recent encoder-decoder model family built upon Gemma 3. We adopt the 2B variant of T5Gemma2 as our base model and refer to this model as \mainname-2B. 

\subsubsection{Evaluation Metrics} 
\label{sec:evaluation-metrics}
To evaluate the quality of code generation, we adopt the metrics below, which respectively measure the correctness, effectiveness, and type correctness:

\begin{itemize}
    \item \textbf{Pass@k (k=1,10)~\cite{DBLP:journals/corr/abs-2107-03374}}: These metrics quantify the proportion of problems where at least one of the top-k generated candidates passes all reference test cases. Each generated candidate is executed against the test cases provided in the benchmark, and a candidate is considered correct only if it produces the expected output for all test cases. 
    %It's the standard and widely used method to quantify the correctness of generated code.

    \item \textbf{First Success Position (FSP)}: This metric is the mean rank of the first functionally correct candidate among the generated ones across the test set. It measures how early in the candidate list a correct solution appears, assessing the efficiency of output ranking.

    \item \textbf{Compilation Error Rate (CER)}: This metric quantifies the proportion of generated candidates that fail to compile. 
    Since \mainname generates programs with type correctness guarantees, CER reflects the type system's effectiveness in catching compile-time errors. 
\end{itemize}

\subsubsection{Implementation Details}

We fine-tuned both \mainname-220M (based on CodeT5-220M) and \mainname-2B (based on T5Gemma2-2B) following a standard procedure with the same set of hyperparameters to ensure a fair comparison. Each model was fine-tuned on the training set until convergence, with multiple checkpoints saved throughout the process. The best-performing checkpoint is used for evaluation.
Since \mainname introduces a new representation that differs from standard code tokens, we perform an initial fine-tuning phase using a supervised fine-tuning dataset from OpenCoder~\cite{DBLP:journals/corr/abs-2411-04905} to help the model adapt to this representation.

\mainname consistently improves code generation accuracy at both scales and on every benchmark.
%
On SuFu, \mainname-220M improves pass@10 from 32.76\% (CodeT5-220M) to 46.55\%, and \mainname-2B improves it from 37.93\% (T5Gemma2-2B) to 50.00\%. On MBJP, \mainname-220M improves pass@10 from 20.90\% to 28.36\%, and \mainname-2B improves pass@1 from 13.43\% to 25.37\% and pass@10 from 32.84\% to 43.28\%.
The gains carry over to both additional Java benchmarks: on HumanEval-Java, \mainname-2B improves pass@1 from 12.50\% to 50.00\% and pass@10 from 25.00\% to 56.25\%; on TransCoder-GFG, it improves pass@1 from 13.59\% to 30.10\% and pass@10 from 27.18\% to 46.60\%.
The improvements are particularly pronounced on SuFu, indicating that \mainname enhances the model's ability to reason about type constraints on languages with complex type systems and limited training data.

We scope the claims on the two additional Java benchmarks explicitly.
Both benchmarks are normalized to the MBJP task style and share its training pipeline, so they measure in-distribution extension of the MBJP setting rather than zero-shot generalization to their raw task distributions.
Within this scope, the HumanEval-Java comparison is ancestor-mixed as noted in \autoref{tab:model-results}, and the TransCoder-GFG comparison is fail-closed.

In terms of the position of the first successful prediction (FSP), \mainname consistently reduces FSP compared to the corresponding base models on every benchmark: for example, \mainname-2B reduces FSP from 7.46 to 6.36 on MBJP, from 7.88 to 4.75 on HumanEval-Java, and from 7.74 to 5.81 on TransCoder-GFG.

Most notably, \mainname greatly reduces compilation errors, as indicated by the CER numbers.
In SuFu, all compilation errors are caused by type errors, so \mainname completely eliminates compilation errors (CER = 0.00\%). 
In Java, compilation errors may also be triggered by static analysis, which is uncaptured in our implemented type system(e.g., unreachable code), which is why \mainname retains a small CER.
Under the revised protocol, the ordinary T5Gemma2-2B baseline fails to compile 25--30\% of its candidates on the three Java benchmarks, while \mainname-2B reduces CER to 0.45\% on MBJP, 1.30\% on HumanEval-Java, and 2.75\% on TransCoder-GFG.

Overall, \mainname achieves clear performance gains and significant improvements in code correctness and reliability across model scales and benchmarks, fulfilling our design objectives.
A task-level failure analysis in Appendix~\ref{appendix-failure} further shows that the residual failures of \mainname are dominated by well-typed but semantically wrong programs, while invalid generation essentially disappears as a failure mode.

Starting from the base setting, each subsequent enhancement contributes meaningfully to the overall improvement in code generation quality and reliability. 

Syntactic pruning improves pass@1 by +3.45\% and reduces CER by 2.13\%, demonstrating that basic structural constraints help filter trivially invalid outputs.

The statistics quantify the two pruning components.
The syntactic mask provides the bulk of the search-space reduction, eliminating 59.1\% of the vocabulary at every decoding step on average, which bounds the branching factor the LM faces at each decision.
The type component constructs the derivation tree step by step and rejects 8.2\% of the grammar-surviving expansions whose synthesis rule cannot extend it.
The low per-step rate is itself evidence for the representation: trained on decision sequences, the LM already proposes mostly type-extendable derivations, so the component's work concentrates on the tail---it rejects 21.2\% of finished programs at the output boundary, eliminating the ill-typed survivors that would otherwise keep the compilation error rate above zero.
This construction-time pruning, together with the fused output-boundary verification of the same component, is what keeps the compilation error rate at zero.
No single component is sufficient: the type component operates on candidates the syntactic mask already admitted, and correctness by construction is realized only when the complete derivation verifies.

Two distinct phenomena must be separated when reporting search failures.
Beam-search exhaustion in the strict sense---pruning eliminates every live beam so that the search cannot continue---never occurs in the instrumented run (0 of 58 tasks): the syntactic mask is derived from the grammar and always leaves at least one legal continuation for the current derivation state, and among the twenty highest-scoring expansions at least one always extends the derivation.
The decoder therefore never needs a fallback to unconstrained generation; the only fallback policy is fail-closed scoring.
What the fixed budget does produce is completion shortfall, reported per ablation configuration: syntactic pruning alone slightly reduces the shortfall relative to the unchecked base (15.9\% vs.\ 19.0\%), because masking dead-end tokens early helps the beam complete candidates, whereas adding type pruning raises it to 34.1\% and the full configuration to 37.8\%---each additional correctness guarantee is paid for with a lower completion rate within the budget.
This quantifies the gap discussed in \autoref{sec:soundness-completeness}: the completeness theorem guarantees that a synthesis derivation exists for every well-typed program, but how many derivations beam search completes within a fixed budget is an empirical property of the trained model and its pruning components, not a consequence of the theory.

\subsubsection{RQ3: Comparison with Reliability-Oriented Generation Methods}
To answer RQ3, we compare \mainname with methods that pursue correct code by constraining or repairing the output of a trained model.
On SuFu, the baseline is CodeT5-220M with rejection sampling, which repeatedly queries the LM and discards candidate programs that fail to compile until finding sufficient solutions or reaching a resource limit.
On MBJP, we further compare with four approaches that share the same frozen T5Gemma2-2B weights as the ordinary control: (i) \emph{rejection sampling} with a standalone-\texttt{javac} gate and a budget of four ten-draw rounds per task; (ii) \emph{SynCode}~\cite{ugare2024syncodellmgenerationgrammar}, which performs grammar-constrained decoding by masking tokens that violate a Java grammar at each step; (iii) \emph{Repilot}~\cite{DBLP:conf/sigsoft/0003X023}, which fuses LM generation with the Eclipse JDT completion engine for token-level repair; and (iv) \emph{iterative compiler repair}, which regenerates candidates from standalone \texttt{javac} diagnostics for at most two rounds without ever seeing the benchmark tests.
All Java rows are evaluated on the same 67 test tasks with ten candidates per task; the ordinary control is the archived paper-recovery checkpoint (10/67 and 23/67 pass@1/pass@10, close to the submitted row).

On SuFu, rejection sampling provides only minor improvements over the baseline (pass@1 from 24.14\% to 31.03\%, pass@10 unchanged), much less than the improvements achieved by \mainname.
Our budget-limited rejection sampling on the T5Gemma2-2B control behaves the same way: discarding every candidate that fails standalone \texttt{javac} and resampling within a budget of four ten-draw rounds per task leaves pass@1 unchanged (14.93\%) and adds a single task at pass@10 (35.82\%); six tasks cannot even collect ten compilable candidates within the budget.
As a post-hoc filtering technique, it cannot enhance the LM's ability to generate correct code and is thus limited by the candidate quality produced by the base LM.

On MBJP, none of the external reliability baselines improves functional correctness over the ordinary control.
Grammar-constrained SynCode decoding alone preserves the control's solved sets exactly (10/67 and 23/67), so the table reports its stronger compile-safe portfolio variant, which adds a standalone-\texttt{javac} gate and yields one additional solved task at pass@10 (24 vs.~23 of 67) while reducing compile errors from 122 to 73 of 670 candidates, at the cost of a second generation arm.
Repilot retains the identical solved sets (10/67 and 23/67) with 112 of 670 compile errors; its JDT checker issues 18{,}653 completion queries and adds 2.66\,ms per output token.
We additionally evaluate iterative compiler repair (not shown in the table): it attains its exact round-0 scores (8/67 and 17/67); compiler feedback repairs 68 candidates' compilability (compile errors 133$\to$83 of 670 over 275 repair calls) but adds no solved task.
In contrast, \mainname-2B solves 17/67 at pass@1 and 29/67 at pass@10, the best of all compared methods, with only 3 of 670 candidates failing to compile.
Paired exact tests over the 67 tasks show that no individual difference between \mainname-2B and any of these baselines reaches significance at the 0.05 level (pass@1 $p \geq 0.09$, pass@10 $p \geq 0.21$), so we present this comparison as a consistent direction shared by all four baselines rather than a statistically proven per-method gap.

These results indicate that external reliability mechanisms---post-hoc filtering, token-level grammar masking, completion-engine repair, or compiler-feedback regeneration---operate on the output distribution of a frozen model: they can prune invalid outputs, but they do not change which programs the model is able to solve.
In contrast, \mainname explicitly incorporates typing rules and typing context during training, enabling the model to learn and utilize type constraints, which improves both correctness and the ranking of candidates.
These results highlight that embedding type information into LMs is substantially more effective than post-hoc pruning approaches, demonstrating the critical importance of \textbf{Type Explicitness} in \autoref{section:intro}.
