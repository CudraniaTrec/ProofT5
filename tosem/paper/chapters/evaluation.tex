\section{Evaluation \label{sec:evaluation}}
We design our evaluation to answer the following research questions.
\begin{itemize}
    \item \textbf{RQ1:} How does \mainname compare with its base models across model scales and benchmarks?
    \item \textbf{RQ2:} How does each component of \mainname contribute to the overall performance, and what runtime cost does it introduce?
    \item \textbf{RQ3:} How does \mainname compare with other reliability-oriented generation approaches, including rejection sampling, token-level constrained decoding, completion-engine repair, and iterative compiler-feedback repair?
    \item \textbf{RQ4:} How does \mainname compare with variants that generate the type derivation tree and the program separately instead of simultaneously?
\end{itemize}

\subsection{Experimental Setup}

\subsubsection{Benchmark}
To evaluate the generality of \mainname, our evaluation considers two languages with very different characteristics, SuFu~\cite{DBLP:journals/pacmpl/JiZPXH24} and Java.
%Correspondingly, we used two datasets: the SuFu dataset and the MBJP~\cite{DBLP:conf/iclr/AthiwaratkunGWL23} dataset.
\begin{itemize}
 \item \textbf{SuFu} is an ML-style functional language designed for automatic program optimization. This language uses a customized type system for extracting operations for optimization on data structures.
 %
 This language has limited code resources, making it representative for evaluating \mainname under low-resource conditions.

 We collect SuFu programs from its GitHub repository, which comprises 290 programs with test cases. For each program, we manually supply a natural language description, along with the relevant inductive definitions and library functions, thus collecting a dataset of code generation tasks.
 %
 This dataset is then split randomly into a training set of 80\% tasks and a test set of 20\% tasks.
 
 \item \textbf{Java} is a popular imperative language with a sophisticated type system. In a balance between the implementation cost and the expressiveness, we implement a subset of Java that preserves its core syntax while omitting advanced features like lambda expressions.

 We consider the MBJP dataset~\cite{DBLP:conf/iclr/AthiwaratkunGWL23} in our evaluation, which is the Java version of the popular MBPP dataset. Our Java subset covers the MBJP tasks admitted by our toolchain, which we split randomly into a training set of 608 tasks and a held-out test set of 67 tasks.

 \item \textbf{HumanEval-Java} and \textbf{TransCoder-GFG} are two additional Java benchmarks that broaden the evaluation beyond MBJP. HumanEval-Java normalizes the Java port of HumanEval~\cite{DBLP:journals/corr/abs-2107-03374} into the MBJP prompt and test-harness format, and TransCoder-GFG does the same for the GeeksForGeeks programs released with TransCoder~\cite{DBLP:conf/nips/LachauxROC20}. 
HumanEval-Java uses a fixed split of 146 training and 16 test tasks, and TransCoder-GFG uses a fixed split of 414 training and 103 test tasks.
\end{itemize}

More information about SuFu, Java, and the dataset construction can be found in Appendix~\ref{appendix-benchmark}.

\subsubsection{Models}
We implement \mainname based on CodeT5~\cite{DBLP:conf/emnlp/0034WJH21}, a family of encoder-decoder models for code understanding and generation. We adopt the 220M variant of CodeT5 as our base model for subsequent training and refer to our model as \mainname-220M. 
We also evaluate \mainname on T5Gemma2~\cite{zhang2025t5gemma2seeingreading}, a more recent encoder-decoder model family built upon Gemma 3. We adopt the 2B variant of T5Gemma2 as our base model and refer to this model as \mainname-2B. 

\subsubsection{Evaluation Metrics} 
\label{sec:evaluation-metrics}
To evaluate the quality of code generation, we adopt the metrics below, which respectively measure the correctness, effectiveness, and type correctness:

\begin{itemize}
    \item \textbf{Pass@k (k=1,10)~\cite{DBLP:journals/corr/abs-2107-03374}}: These metrics quantify the proportion of problems where at least one of the top-k generated candidates passes all reference test cases. Each generated candidate is executed against the test cases provided in the benchmark, and a candidate is considered correct only if it produces the expected output for all test cases. 
    %It's the standard and widely used method to quantify the correctness of generated code.

    \item \textbf{First Success Position (FSP)}: This metric is the mean rank of the first functionally correct candidate among the generated ones across the test set. It measures how early in the candidate list a correct solution appears, assessing the efficiency of output ranking.

    \item \textbf{Compilation Error Rate (CER)}: This metric quantifies the proportion of generated candidates that fail to compile. 
    Since \mainname generates programs with type correctness guarantees, CER reflects the type system's effectiveness in catching compile-time errors. 
\end{itemize}

\subsubsection{Implementation Details}

We fine-tuned both \mainname-220M (based on CodeT5-220M) and \mainname-2B (based on T5Gemma2-2B) following a standard supervised fine-tuning procedure with the same set of hyperparameters to ensure a fair comparison. Each model was fine-tuned on the training set until convergence. 
Since \mainname introduces a new representation that differs from standard code tokens, we perform an initial training phase using a supervised fine-tuning dataset from OpenCoder~\cite{DBLP:journals/corr/abs-2411-04905} to help the model adapt to this representation.

\mainname improves code generation accuracy at both scales and on every benchmark, with the largest gains on SuFu where the type constraints exploit a complex type system under low-resource conditions.
The 220M MBJP pass@1 gain is modest (10.45\% to 11.94\%) because the type constraints mainly remove uncompilable candidates; the benefit shows up in pass@10, FSP, and CER instead, consistent with the failure analysis in Appendix~\ref{appendix-failure} (well-typed but wrong is the dominant residual mode).
\mainname{} also drops CER to 0.00\% on SuFu and 0.45\% / 1.30\% / 2.75\% on the three Java benchmarks; the small residual Java CER comes from static-analysis errors the type system does not capture.

To contextualize absolute performance, \autoref{tab:decoder-only-compare} reports three larger decoder-only models (MiMo-7B, Qwen3-14B, Qwen3-30B-A3B; 7B--30B parameters), prompted with the same MBJP-normalized task prompt in all conditions, alongside the two fine-tuned 2B encoder-decoder models as protocol-different references.
Each prompted model produces one greedy candidate per task: the zero-shot condition uses only the task prompt, and the few-shot condition prepends three solved examples for the Java benchmarks (three fixed synthetic Java examples, so no benchmark solution is copied into the prompt) and six train-only examples for SuFu.
On Java these models are difficult to beat: they solve 33--45 of 67 MBJP tasks, 3--14 of 16 HumanEval-Java tasks, and 38--52 of 103 TransCoder-GFG tasks, well above the fine-tuned 2B models, and HumanEval-Java in particular is close to saturated for the strongest of them.
On SuFu the picture reverses: none of the three solves a single task zero-shot, and few-shot prompting reaches at most 8 of 58, whereas \mainname-2B solves 25; the low-resource language is where the type-guided representation delivers its advantage.
The few-shot behaviour carries a further observation: for the two Qwen3 models, few-shot prompting yields no Java gain over zero-shot (14B: $42{\to}41$ on MBJP, $14{\to}11$ on HumanEval-Java, $50{\to}49$ on TransCoder-GFG; 30B: $42{\to}45$, $13{\to}14$, $52{\to}52$) and helps only on SuFu ($0{\to}6/8$); MiMo-7B is the exception, gaining substantially on two Java benchmarks ($3{\to}10$ on HumanEval-Java, $38{\to}43$ on TransCoder-GFG).
Since the effect is model-dependent, we do not claim benchmark contamination; we note only that demonstrating the target format is uninformative exactly where zero-shot performance is already high, which is consistent with these long-standing Java benchmarks being well represented in web-scale pretraining data, and we therefore read the Java columns as evidence that the external bar is high rather than as a like-for-like method comparison.
Within the controlled fine-tuned pair, \mainname-2B solves more tasks than its base model T5Gemma2-2B on all four benchmarks (17 vs.\ 9 on MBJP, 8 vs.\ 5 on HumanEval-Java, 31 vs.\ 20 on TransCoder-GFG, and 25 vs.\ 17 on SuFu).

Type-based mechanisms are the ones that eliminate compilation errors; dynamic typing context is what pushes pass@10 and FSP to their final values, demonstrating \textbf{Context Locality} in~\autoref{section:intro}.

Instrumenting the constrained decoder on the 58 SuFu tasks (beam 10, 330-step budget): syntactic pruning eliminates 59.1\% of vocabulary proposals per beam step, and type pruning eliminates 8.2\% of the 167{,}295 grammar-valid expansions; the constrained search dead-ends on none of the 58 tasks.
At the output boundary the type component rejects 21.2\% of the 533 completed candidates (113 rejections): incremental checking during search is deliberately permissive while an AST field is incomplete, so whole-program type validity is established only on the complete derivation.

Inference cost is reported along two dimensions in \autoref{tab:ablation-combined}: per-task wall time and wall time per decoding step.
Each component strictly increases the per-step cost ($31.1 \to 32.4 \to 43.7 \to 59.6$\,ms), while the per-task total moves by $-6.38\%$ / $+94.00\%$ / $+173.88\%$ ($2.74\times$ base); all four runs complete all 58 tasks, and slots that miss the fixed budget count as failures (fail-closed), with the decoder never falling back to unconstrained generation.
The $-6.38\%$ of syntactic pruning is a net effect, not a faster checker: the search stops once every beam completes, and masking ill-formed decisions keeps beams on well-formed derivations that finish sooner (a mean of 164.6 versus 183.2 decoding steps per task), so the roughly $+4\%$ per-step masking cost is outweighed by the $10\%$ fewer steps (a re-run of both configurations reproduced $5.66$ versus $5.32$\,s and the same step counts).
Qualitatively, the synthesis tree grows with the number of typing-rule applications, so more complex programs produce deeper trees, longer decision sequences, and more rule choices at each node; our measurements characterize this on SuFu but do not bound the behavior on richer language features.

\subsubsection{RQ3: Comparison with Reliability-Oriented Generation Methods}
To answer RQ3, we compare \mainname{} with methods that pursue correct code by constraining or repairing the output of a trained model.
On SuFu the baseline is CodeT5-220M with rejection sampling; on MBJP we compare four approaches that share the same frozen T5Gemma2-2B weights as the ordinary control: \emph{rejection sampling} with a standalone-\texttt{javac} gate (four ten-draw rounds per task); \emph{SynCode}~\cite{ugare2024syncodellmgenerationgrammar} (grammar-constrained token masking); \emph{Repilot}~\cite{DBLP:conf/sigsoft/0003X023} (LM + Eclipse JDT completion engine); and \emph{iterative compiler repair}, which regenerates candidates from standalone \texttt{javac} diagnostics for at most two rounds without ever seeing the benchmark tests; the repair rounds use the un-fine-tuned T5Gemma2-2B as the repair agent, since the fine-tuned generator never learned to consume diagnostics.
All Java rows are evaluated on the same 67 tasks with 10 candidates each; the ordinary control uses an archived T5Gemma2-2B checkpoint (10/67 and 23/67), which differs slightly from \autoref{tab:model-results} (13.43/32.84) because the external methods must share one frozen distribution; the \mainname-2B row is identical in both tables.

On SuFu, rejection sampling with CodeT5-220M only lifts pass@1 from 24.14\% to 31.03\%; the budget-limited variant on the T5Gemma2-2B control leaves it unchanged (14.93\%), confirming that post-hoc filtering cannot change which programs a base LM can solve.
On MBJP, none of the four external baselines improves functional correctness over the ordinary control: Repilot adds 2.66\,ms/token and 18{,}653 JDT queries but no new solved task; iterative repair repairs 32 candidates' compilability (compile errors 122$\to$90 of 670) yet leaves the solved sets exactly unchanged; paired exact tests show no difference reaching significance (pass@1 $p \geq 0.09$, pass@10 $p \geq 0.21$).
\mainname-2B solves 17/67 at pass@1 and 29/67 at pass@10 with 3 of 670 candidates failing to compile, the best of all compared methods.
External reliability mechanisms (post-hoc filtering, token-level grammar masking, completion-engine repair, compiler-feedback regeneration) act on a frozen output distribution and prune invalid outputs but cannot change which programs the model solves; \mainname{} embeds type constraints into the LM itself, demonstrating \textbf{Type Explicitness} in~\autoref{section:intro}.

\subsection{Limitations}
The current architecture is designed for encoder-decoder models: at each synthesis step, an encoder processes the evolving synthesis goal to provide the dynamic typing context. A decoder-only adaptation could be more efficient, but it would require a different representation in which type-rule tokens are used to encode the program and guide syntactic and type pruning. Such a redesign would not retain the current dynamic typing-context mechanism, and we leave it to future work.

Our implementation and experiments also focus on languages with explicit typing rules, namely SuFu and the evaluated Java subset. We have not established that the current formulation applies to dynamically typed languages such as Python, where the relevant type information is not supplied by the same kind of static typing derivation.

Both evaluated type systems are deliberately simple. The implemented Java subset omits polymorphism with variance, subtyping hierarchies, overload resolution, type inference beyond local declarations, and mutable-state-related features; SuFu's type system targets fusion optimization. Richer features would enlarge the rule set, increase the branching factor at individual synthesis nodes, and, for polymorphism, potentially require higher-order unification (Sec.~\ref{sec:meta}); our measurements on SuFu and the Java subset do not establish how the approach scales to such languages.

The simply typed lambda calculus used in the overview serves a pedagogical role and is simpler still; the distance between it and industrial languages is bridged only partially by the evaluated Java subset.
